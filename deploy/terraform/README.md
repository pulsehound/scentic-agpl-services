# Provisioning the AGPL services

<!-- SPDX-License-Identifier: AGPL-3.0-or-later -->

Three services and three datastores, in Scentic's existing project and VPC.

| | Ingress | Store |
|---|---|---|
| `scentic-agpl-gateway` | **internal only** | Cloud SQL Postgres |
| `scentic-agpl-kimai` | **internal only** | Cloud SQL MySQL |
| `scentic-agpl-opensign` | **public** | MongoDB on a VM |

OpenSign is public because it has to be: the people signing are usually the
other side of a transaction, following a link from an email, with no account and
no VPN. Everything else is unreachable from outside the VPC. That asymmetry is
the security boundary of this integration.

Sharing a VPC with Scentic is not a licence question. What keeps Scentic out of
AGPL is that these are separate programs in separate processes talking HTTP —
see `docs/SCENTIC_AGPL_CONNECTION_MANUAL.md`.

## Before you start

You need a provisioning identity. The account that deploys Scentic deliberately
cannot create databases, secrets or networks, and should stay that way:

```bash
PROJECT=causal-hour-502018-c8
gcloud iam service-accounts create scentic-agpl-provisioner \
  --project="$PROJECT" --display-name="AGPL stack provisioner"

for role in roles/cloudsql.admin roles/secretmanager.admin \
            roles/compute.admin roles/run.admin \
            roles/iam.serviceAccountAdmin roles/iam.serviceAccountUser \
            roles/resourcemanager.projectIamAdmin; do
  gcloud projects add-iam-policy-binding "$PROJECT" \
    --member="serviceAccount:scentic-agpl-provisioner@$PROJECT.iam.gserviceaccount.com" \
    --role="$role" --condition=None >/dev/null
done

gcloud iam service-accounts keys create ~/.gcloud-scentic/agpl-provisioner-key.json \
  --iam-account="scentic-agpl-provisioner@$PROJECT.iam.gserviceaccount.com"
```

**Delete it when the stack is up.** It exists to build this once; leaving a
project-admin credential lying around is the thing the narrow deploy account was
created to avoid:

```bash
gcloud iam service-accounts delete \
  "scentic-agpl-provisioner@$PROJECT.iam.gserviceaccount.com" --project="$PROJECT"
```

Also enable the APIs, once:

```bash
gcloud services enable sqladmin.googleapis.com compute.googleapis.com \
  secretmanager.googleapis.com run.googleapis.com --project="$PROJECT"
```

## Apply

```bash
export GOOGLE_APPLICATION_CREDENTIALS=~/.gcloud-scentic/agpl-provisioner-key.json
cd deploy/terraform

terraform init
terraform apply \
  -var="scentic_runtime_service_account=scentic-staging-app@causal-hour-502018-c8.iam.gserviceaccount.com" \
  -var="admin_email=you@scentic.com" \
  -var="gateway_image=us-east1-docker.pkg.dev/causal-hour-502018-c8/scentic-agpl/gateway:<tag>" \
  -var="smtp_host=smtp.example.com" \
  -var="smtp_user=..." \
  -var="smtp_password=..."
```

Every credential is generated by Terraform and written to Secret Manager. None
is printed: outputs deliberately exclude them, because an output lands in
`terraform.tfstate` in plaintext and in the terminal of whoever ran the apply.

## Two things that cannot be provisioned

**Kimai's API token.** Kimai issues it from its own UI after the instance is up
and an administrator has signed in once. So the first apply leaves
`kimai_api_token` empty and the gateway cannot reach Kimai yet. Sign in to the
Kimai URL with `admin_email` and the password in `agpl-kimai-admin-password`,
create an API token, then apply again with `-var="kimai_api_token=..."`.

**OpenSign's signing certificate.** Signed PDFs need a PFX. Without one, OpenSign
runs and records signatures but cannot produce a cryptographically signed
document. Supply one before this is used for anything that matters.

Both are stated here rather than worked around, because a stack that looks
complete and produces unsigned PDFs is worse than one that says what is missing.

## Then point Scentic at it

```bash
terraform output scentic_env
```

Apply those, and Scentic switches from recording locally to connected. The two
HMAC secrets are read from Secret Manager by Scentic's own runtime — they are
one shared value each, held by both sides of the boundary, never copied by hand.

## Tearing it down

```bash
terraform destroy
```

Deletion protection is off on both databases on purpose: this is staging and the
whole point is that it rebuilds from this configuration. Do not carry that
setting into anything holding real data.
