# Scentic ↔ Kimai Entity Mapping

**Status:** AGPL-00 planning document — not yet implemented.
**Scope:** Defines how Scentic core entities map to Kimai entities through the AGPL gateway.
**Audience:** Gateway implementers, Scentic core integration engineers, security reviewers, release-gatekeeper.
**Upstream reference:** Kimai 2.x (PHP/Symfony), REST API at `/api`, API-token auth, `Customer → Project → Activity → Timesheet` model.

---

## 1. Mapping principles

1. **Scentic is the source of truth for identity and Firm structure.** Kimai is the source of truth for time-entry durations and exported state once an entry is locked.
2. **The gateway owns the mapping table, not Scentic core.** Scentic's `ProviderMapping` model is **not** used for AGPL integrations. The gateway stores `scenticEntityType, scenticEntityId, firmId, kimaiEntityType, kimaiEntityId, kimaiTeamId` in its own encrypted-at-rest store. This keeps AGPL knowledge inside the AGPL repo and prevents the proprietary core from depending on Kimai internals.
3. **Every Kimai object is Firm-scoped via Kimai teams.** A Kimai `Team` is created per Scentic Firm. Customers, projects, users, and timesheets are assigned to that team. The gateway never queries Kimai without a `teamId` filter derived from the caller's `firmId`.
4. **Scentic → Kimai is the primary sync direction for creates/updates.** Kimai → Scentic is used only for time-entry changes detected by polling (or Kimai webhooks if configured), and for `exported` state changes.
5. **Names sent to Kimai are sanitized.** A configurable scrubber strips or generalizes confidential tokens (e.g. SSN, account numbers, privileged matter codenames) before any name reaches Kimai.

## 2. Entity mapping overview

| Scentic entity | Kimai entity | Cardinality | Sync direction | Storage of mapping |
|----------------|--------------|-------------|----------------|--------------------|
| Firm | Team (with team membership) | 1:1 | Scentic → Kimai | Gateway mapping table |
| User | User (with API token per user) | 1:1 | Scentic → Kimai | Gateway mapping table (token encrypted) |
| Client | Customer (team-scoped) | 1:1 | Scentic → Kimai | Gateway mapping table |
| Matter | Project (under Customer, team-scoped) | 1:1 | Scentic → Kimai | Gateway mapping table |
| Activity type (enum) | Activity (global or project-specific) | 1:1 | Scentic → Kimai | Gateway mapping table |
| Time entry | Timesheet (user, activity, project, start, end, duration, description) | 1:1 | Bidirectional | Gateway mapping table keyed by `scenticEntryId` |

## 3. Firm → Kimai Team

### 3.1 Field mapping

| Scentic `Firm` field | Kimai `Team` field | Notes |
|----------------------|--------------------|-------|
| `id` (UUID) | — (stored in gateway mapping as `scenticEntityId`) | Never sent to Kimai. |
| `name` | `name` | Sanitized; used as team display name. |
| `active` | — (controls whether gateway allows calls for this Firm) | Kimai team is not deleted on offboard; it is disabled. |
| — | `Team.members` | Set of Kimai user ids belonging to this Firm. |

### 3.2 Lifecycle

- **Create:** `POST /admin/init-firm` → gateway creates a Kimai `Team` with `name = sanitized(firmName)`, stores `firmId → kimaiTeamId` mapping, and provisions a per-Firm Kimai API token stored encrypted.
- **Update:** Firm rename in Scentic triggers `PUT /kimai/firm/{firmId}/mapping` with the new sanitized name. The gateway renames the Kimai team. Renames are rate-limited (max 1/hour) to avoid audit noise.
- **Disable:** `POST /admin/disable-firm` → gateway flips its mapping to `disabled`, revokes the per-Firm Kimai API token, and sets the Kimai team to inactive. Kimai data is **not** deleted unless `deleteUpstreamData=true` with confirmation.
- **Re-enable:** Only via admin action; requires re-init with a new API token.

### 3.3 Authorization rules

- The Kimai team id is the Firm isolation boundary. Every subsequent Kimai API call from the gateway includes `teamId` in the filter set. The gateway rejects any response object whose team membership does not include the caller's `firmId → kimaiTeamId`.
- A Kimai team is never shared between Scentic Firms. The gateway enforces uniqueness: `kimaiTeamId` may map to at most one `firmId`.

## 4. User → Kimai User

### 4.1 Field mapping

| Scentic `User` field | Kimai `User` field | Notes |
|----------------------|--------------------|-------|
| `id` (UUID) | — (gateway mapping) | Never sent to Kimai. |
| `email` | `email` | Required by Kimai; must be unique within the Kimai instance. |
| `firstName` | `firstname` | Optional; if Scentic has no first name, send empty string. |
| `lastName` | `lastname` | Optional. |
| `active` | `enabled` | Scentic user deactivation sets Kimai `enabled=false`. |
| — | `username` | Generated by the gateway as `scentic-<firmSlug>-<userSlug>` to guarantee uniqueness and avoid colliding with non-Scentic Kimai users. |
| — | `apiToken` | Per-user Kimai API token, provisioned by the gateway, stored encrypted. Used for all timesheet writes attributed to this user. |

### 4.2 Lifecycle

- **Create (user added to a Firm):** Gateway creates a Kimai `User`, assigns it to the Firm's Kimai `Team`, provisions an API token, stores `userId → kimaiUserId` mapping with the encrypted token.
- **Update:** Name/email changes propagate. An email change in Scentic triggers a Kimai user email update (Kimai allows it) and a re-verification that the user is still on the Firm's team.
- **Remove from Firm (but still a Scentic user):** Gateway removes the Kimai user from the Firm's Kimai team. The Kimai user account is **not** deleted (it may belong to other Firms in a multi-Firm Kimai instance — though the recommended deployment is one Kimai instance per Scentic tenant, so this case is rare). The per-Firm API token is revoked.
- **Deactivate in Scentic:** Gateway sets Kimai `enabled=false` and revokes all API tokens for that user.

### 4.3 Authorization rules

- A Kimai user is a member of exactly the Kimai teams for the Scentic Firms they belong to. Cross-team membership is rejected by the gateway.
- Timesheet writes are always attributed to the mapped Kimai user using that user's API token, never to a shared service account. This preserves Kimai's per-user audit trail.
- The gateway refuses to create a timesheet for a user who is not a member of the Firm's Kimai team (`403 FIRM_SCOPE_VIOLATION`).

## 5. Client → Kimai Customer

### 5.1 Field mapping

| Scentic `Client` field | Kimai `Customer` field | Notes |
|------------------------|------------------------|-------|
| `id` (UUID) | — (gateway mapping) | Never sent to Kimai. |
| `name` | `name` | Sanitized. |
| `firmId` | `Team.id` (assignment) | The customer is assigned to the Firm's Kimai team. |
| `contactEmail` | `email` | Optional; only sent if Scentic has it and policy allows. |
| `address` | `address` | Optional. |
| `currency` | `currency` | Defaults to Firm currency if unset. |
| `active` | `visible` | Inactive clients become hidden in Kimai. |
| — | `number` | Auto-generated by Kimai or set by gateway as `SC-<clientId-suffix>`. |
| `taxRate` | `taxRate` | Optional. |

### 5.2 What is NOT sent to Kimai

- Client legal entity type, jurisdiction, risk score, conflict checks, intake notes, privileged contact notes, billing arrangements beyond currency, any custom Scentic client fields not listed above.

### 5.3 Lifecycle

- **Create:** `PUT /kimai/firm/{firmId}/clients/{clientId}/mapping` → gateway creates a Kimai `Customer` assigned to the Firm's team, stores mapping.
- **Update:** Name/contact changes propagate (sanitized). Re-assignment to a different Firm is rejected (clients are Firm-scoped in Scentic).
- **Deactivate:** Set Kimai `visible=false`. Timesheets referencing this customer remain accessible for historical reporting.

### 5.4 Authorization rules

- A Kimai `Customer` is assigned to exactly one team (the Firm's). Kimai allows multi-team customers; the gateway restricts to one team to enforce Firm isolation.
- The gateway verifies, on every customer read/write, that the customer's team id matches the caller's `firmId → kimaiTeamId`. Mismatch → `403 FIRM_SCOPE_VIOLATION`.

## 6. Matter → Kimai Project

### 6.1 Field mapping

| Scentic `Matter` field | Kimai `Project` field | Notes |
|------------------------|-----------------------|-------|
| `id` (UUID) | — (gateway mapping) | Never sent to Kimai. |
| `name` | `name` | **Sanitized and optionally generalized.** Matter names often contain sensitive info; a per-Firm policy controls whether the real name or a billing code is sent. |
| `clientId` | `customer` (id) | Must resolve to a Kimai Customer in the same Firm. |
| `firmId` | `Team.id` (assignment) | Project assigned to the Firm's team. |
| `matterCode` | `orderNumber` | Optional; useful for invoice matching. |
| `currency` | `currency` | Defaults to client currency. |
| `active` | `visible` | Closed matters become hidden. |
| `billable` | `billable` | Default `true`. |
| `budgetedHours` | `budget` (hours) | Optional. |
| — | `start` / `end` | Optional; if Scentic tracks matter open/close dates. |

### 6.2 What is NOT sent to Kimai

- Matter description, parties, opposing counsel, privileged notes, documents, conflict info, status beyond active/closed, custom Scentic matter fields. Kimai receives only what is needed for time tracking and billing.

### 6.3 Lifecycle

- **Create:** `PUT /kimai/firm/{firmId}/matters/{matterId}/mapping` → gateway creates a Kimai `Project` under the mapped Customer, assigned to the Firm's team.
- **Update:** Name changes propagate subject to sanitization. Client reassignment (matter moved to a different client in Scentic) triggers a Kimai project customer re-assignment **only if** the new client is in the same Firm; cross-Firm matter moves are rejected.
- **Close:** Set Kimai `visible=false` and `end=date`. Timesheets remain.

### 6.4 Authorization rules

- The gateway verifies `project.customer.teamId === firmId.kimaiTeamId` on every project read/write.
- A project must belong to exactly one team.

## 7. Activity type → Kimai Activity

Scentic defines a fixed enum of activity types. Each maps to a Kimai `Activity`.

### 7.1 Scentic activity enum

`RESEARCH`, `DRAFTING`, `REVIEW`, `CALL`, `COURT`, `MEETING`, `TRAVEL`, `ADMIN`, `FILING`, `DISCOVERY`, `NEGOTIATION`, `OTHER`.

### 7.2 Field mapping

| Scentic activity type | Kimai `Activity` field | Notes |
|------------------------|------------------------|-------|
| enum value | `name` | Display name (e.g. `Drafting`). |
| — | `activityNumber` | Auto-generated. |
| — | `project` | Set only for `scope=project` activities. |
| `billable` (per type policy) | `billable` | Default `true` for `DRAFTING`, `COURT`, etc.; `false` for `ADMIN`. |
| — | `visible` | Always `true` unless disabled. |

### 7.3 Scope: global vs project

- **Global activities** are recommended as the default. One Kimai global `Activity` per Scentic activity type, shared across all projects in the Firm. Reduces Kimai clutter.
- **Project-specific activities** are used only when a Firm requires per-matter billing rates or descriptions per activity type. In that case the gateway creates a project-scoped Activity under the mapped Project.

### 7.4 Lifecycle

- **Init:** During `POST /admin/init-firm`, the gateway creates the standard set of global activities for the Firm (one per Scentic enum value) unless they already exist.
- **Add activity type:** If Scentic extends the enum, the gateway creates the missing global Activity on next mapping call.
- **Disable:** Setting an activity type inactive in Scentic hides the Kimai Activity. Existing timesheets remain.

## 8. Time entry → Kimai Timesheet

### 8.1 Field mapping

| Scentic `TimeEntry` field | Kimai `Timesheet` field | Notes |
|----------------------------|-------------------------|-------|
| `id` (UUID) | — (gateway mapping as `scenticEntryId`) | Never sent to Kimai as a field; stored in mapping. |
| `userId` | `user` (id) | Resolved via user mapping. |
| `matterId` | `project` (id) | Resolved via matter mapping. |
| `activityType` | `activity` (id) | Resolved via activity mapping. |
| `startAt` | `begin` | ISO datetime. |
| `endAt` | `end` | ISO datetime; `null` for running entries. |
| `durationSeconds` | `duration` (computed by Kimai) | Gateway sends start/end; Kimai computes duration. |
| `description` | `description` | **Scrubbed** before forwarding. |
| `billable` | `billable` | Defaults from project/activity. |
| `rate` | `hourlyRate` / `fixedRate` | Optional. |
| `exported` | `exported` | Set only via `POST /.../export`. |
| — | `tags` | Optional; gateway may add `scentic-synced` tag for traceability. |

### 8.2 What is NOT sent to Kimai

- Time entry internal notes marked privileged, linked documents, matter context beyond the project id, user location, device info, custom Scentic time-entry fields not listed above.

### 8.3 Lifecycle (bidirectional)

- **Scentic → Kimai (create):** `POST /kimai/.../time-entries` creates a Kimai timesheet. Gateway stores `scenticEntryId ↔ kimaiTimesheetId`.
- **Scentic → Kimai (update):** `PUT /kimai/.../time-entries/{entryId}` updates the Kimai timesheet, unless it is `exported` (locked). Locked updates return `409 ENTRY_EXPORTED`; Scentic must un-export or create an adjustment entry.
- **Scentic → Kimai (delete):** `DELETE` soft-deletes (Kimai "trash"). Hard delete requires confirmation.
- **Kimai → Scentic (polling):** The gateway polls `GET /kimai/.../time-entries` on a configurable interval (default 60s) per Firm, compares against the last-seen state, and emits `kimai.time.entry.*` webhooks to Scentic for changes detected in Kimai (e.g. a user edits a timesheet directly in Kimai's UI). This is the only path by which Kimai-originated changes reach Scentic.
- **Kimai → Scentic (webhooks, optional):** If Kimai webhooks are configured, the gateway registers a webhook endpoint in Kimai and forwards events as `kimai.time.entry.*` webhooks. This replaces polling for those Firms.

### 8.4 Conflict resolution

1. **Same entry updated in both systems between syncs:** The gateway compares `updatedAt` timestamps. The later one wins. If timestamps are within a 5-second tie window, the Scentic version wins (Scentic is the primary UI). The losing side is reconciled by a follow-up update in the winning direction. The conflict is logged as an audit event `kimai.time.conflict` with both versions' metadata (not description text).
2. **Entry exported in Kimai but not yet known to Scentic:** The gateway emits a `kimai.time.entry.exported` webhook so Scentic can mark its copy as locked. Subsequent Scentic updates are rejected by the gateway with `409 ENTRY_EXPORTED`.
3. **Entry deleted in Kimai but still present in Scentic:** The gateway emits `kimai.time.entry.deleted`. Scentic must decide whether to soft-delete its copy or recreate the Kimai entry. Default policy: Scentic soft-deletes its copy and logs the discrepancy.
4. **Entry deleted in Scentic but still present in Kimai:** The gateway soft-deletes the Kimai timesheet on next sync.
5. **User/matter/activity unmapped at create time:** `404 MAPPING_NOT_FOUND`. Scentic must create the mapping before retrying. The time entry is not created in either system.

## 9. Sync direction matrix

| Operation | Primary direction | Trigger | Notes |
|-----------|-------------------|---------|-------|
| Firm/User/Client/Matter/Activity create | Scentic → Kimai | Scentic lifecycle event → mapping call | Idempotent. |
| Firm/User/Client/Matter/Activity update | Scentic → Kimai | Scentic lifecycle event | Sanitized. |
| Firm/User/Client/Matter/Activity deactivate | Scentic → Kimai | Scentic lifecycle event | Soft (hide/disable). |
| Time entry create | Scentic → Kimai | User action in Scentic | Idempotent by `scenticEntryId`. |
| Time entry update | Scentic → Kimai (primary) / Kimai → Scentic (polling) | Either side | Conflict rules in §8.4. |
| Time entry delete | Scentic → Kimai (primary) / Kimai → Scentic (polling) | Either side | Soft-delete first. |
| Time entry export/lock | Scentic → Kimai | Billing run in Scentic | One-way; unlock is admin-only. |
| Time entry export status change in Kimai | Kimai → Scentic | Polling/webhook | Scentic marks locked. |

## 10. Authorization rules summary

1. **Firm scoping:** Every Kimai API call from the gateway is filtered by the caller's `firmId → kimaiTeamId`. The gateway post-filters every response to ensure each returned object's team membership includes that team id. Any object that does not is dropped and logged as `kimai.scope.leak` (security event).
2. **Team isolation:** A Kimai team maps to exactly one Scentic Firm and vice versa. No shared teams.
3. **User scoping:** A timesheet's `user` must be a member of the Firm's team. The gateway rejects timesheet creates for users not on the team.
4. **Per-user API tokens:** Timesheet writes use the mapped user's API token, not a shared admin token. This preserves Kimai's per-user audit and limits blast radius (see threat model: overbroad service account).
5. **Admin-only operations:** Firm init/disable, secret rotation, and mapping repairs require admin-level tokens, not regular user tokens.

## 11. Data minimization rules

| Data category | Sent to Kimai? | Reason |
|---------------|----------------|--------|
| Firm name | Yes (sanitized) | Required for team display. |
| User email, first/last name | Yes | Required for Kimai user account. |
| Client name, contact email, address | Yes (sanitized, optional) | Needed for customer record and invoicing. |
| Matter name | Yes, but **sanitized and optionally replaced with a billing code** per Firm policy | Matter names are high-risk; configurable. |
| Matter parties, opposing counsel, notes | **No** | Not needed for time tracking. |
| Activity type | Yes (as activity name) | Needed for timesheet categorization. |
| Time entry description | Yes, **scrubbed** (deny-list patterns removed) | Needed for billing narratives. |
| Time entry privileged notes | **No** | Privileged content never leaves Scentic. |
| Time entry linked documents | **No** | Not needed for time tracking. |
| Financial rates | Yes (per entry, optional) | Needed for billing. |
| Scentic internal ids | **No** (stored in gateway mapping only) | Not relevant to Kimai. |
| Service tokens, API tokens | **No** (used for auth only, never logged) | Secrets. |

## 12. Mapping storage

- **Location:** Gateway-managed store (Postgres table `gateway_mappings` in the gateway's own database, or Redis hash for hot lookups backed by Postgres). **Not** Scentic's `ProviderMapping` table.
- **Schema (logical):**

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid | PK. |
| `firm_id` | uuid | Scentic Firm id. |
| `scentic_entity_type` | enum (`FIRM`, `USER`, `CLIENT`, `MATTER`, `ACTIVITY`, `TIME_ENTRY`) | |
| `scentic_entity_id` | uuid | Scentic entity id. |
| `kimai_entity_type` | enum (`TEAM`, `USER`, `CUSTOMER`, `PROJECT`, `ACTIVITY`, `TIMESHEET`) | |
| `kimai_entity_id` | string | Kimai numeric/string id. |
| `kimai_team_id` | int | Denormalized for fast scope checks. |
| `api_token_encrypted` | bytea | Nullable; per-user or per-Firm token, encrypted at rest. |
| `status` | enum (`ACTIVE`, `DISABLED`, `DELETED`) | |
| `created_at`, `updated_at` | timestamptz | |
| `version` | int | Optimistic concurrency. |

- **Unique constraints:**
  - `(firm_id, scentic_entity_type, scentic_entity_id)` — one Scentic entity maps to one Kimai entity.
  - `(kimai_entity_type, kimai_entity_id)` — a Kimai entity maps to at most one Scentic entity (prevents cross-Firm aliasing).
- **Encryption:** `api_token_encrypted` uses envelope encryption with a KMS-managed key in production. The plaintext token is held only in memory during an upstream call.
- **Access:** Only the gateway process and gateway admin tooling can read this store. Scentic core has no direct access.

## 13. Open questions (AGPL-00)

- Default sanitization rules for matter names (allow real name vs. billing code) — needs per-Firm policy decision.
- Whether to deploy one Kimai instance per Scentic tenant (recommended) or a shared Kimai instance with strict team isolation. Affects user-email uniqueness constraints.
- Whether Kimai webhooks are configured in production or whether Scentic always polls.
- Polling interval per Firm and the cost of polling across many Firms at scale.
- Whether the gateway should support Kimai "global activities" only or also project-scoped activities from day one.
